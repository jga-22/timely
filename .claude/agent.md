# Timely: agent context

Shared context for any Claude Code session working on this repo. Read it first, then the specs it points to. Keep it short and current: update it when a decision, convention or open item changes.

## What this is

Timely is a local-first planning app. It combines two ideas:

- **The why (goals):** a Harada grid. One 5-year ambition, 8 life areas (categories), each with a 5-year goal, a 1-year target and measurable daily habits.
- **The time (planner):** a weekly template of hour slots, applied across the 52 or 53 weeks of the year. Home shows today; Insights charts the planned hours of one year or several.

The link between them is the product: a habit points at an activity, Goals compares the time the habits ask for with the time scheduled for their categories, and Insights shows where the planned hours go.

The owner is a solo developer. The app is still in dev mode: no production users, no backward compatibility needed.

## Stack and commands

Nuxt 4, Vue 3, Pinia, Vuetify (neutralised, see the style spec), TypeScript. State persists in browser `localStorage` by default; persistence is pluggable (Supabase is the optional remote mode, see below). There is no Timely backend.

```bash
npm run dev                 # dev server (dev-only 404s for Vuetify/mdi @fs CSS are known and harmless)
npm run build               # production build; must stay clean
npx nuxi typecheck          # must stay at 0 errors
```

If `npx nuxi typecheck` cannot resolve vue-tsc, run `npm i --no-save vue-tsc@3 @vue/language-core@3` (never commit that to `package.json` or the lockfile).

## Model and decisions

- **One list of categories.** Goal dimensions and planner categories are the same thing. `Category` has `id, name, color, order` plus `goal5y, target1y, targetTbd`. The first 8 categories by `order` form the 3x3 Goals grid. Categories are managed in Goals (list and detail edit mode); activities are managed in Planner. In the UI the categories are called life areas; the code keeps `category`.
- **Activities are a separate level** under a category. **Habits** belong to a category, are measurable (frequency count per day/week/month plus optional `minutesPerOccurrence`) and may link to an activity. A habit can make its own activity from its form (FR-GOALS-24, `ownActivityFor` in the store): the activity has the habit's name and life area; renaming the habit does not rename it.
- **Goals comparison (FR-GOALS-16):** per category, needed = the time the habits ask for (habits with minutes per occurrence). Allocated = scheduled hours a week in the Goals week type (`goalsTemplate`: the active one, or while the active one is time off, the working one with most assigned weeks) of the activities linked from the category's habits and the activities that list it as secondary (each once). Primary membership alone does not count. Status `under`, `over`, `ok` (within the larger of 30 min and 10%) or `none` (no time target). Per habit: the linked activity's hours against the need, or Not linked. Shown as the needed-and-planned bar with a status icon and text (`NeededPlannedBar.vue`) in each list row and the category detail. No outline, no legend; status is never colour only.
- **Activities have one primary category and optional secondary ones.** `categoryId` is the primary category: it gives the colour and the listing, and Insights counts each activity once there, so its shares add up to 100. `alsoCategoryIds?: string[]` lists other categories whose comparison also counts the hours (never the primary one; the Planner form offers them as "Also counts toward").
- **One entry, one form (FR-ITEM).** The user sees one kind of item, "Activities and habits". An entry is a habit with its linked activity, or an activity that no habit links to; the stored objects keep their shape. `app/utils/entries.ts` reads them into one draft (`entryDraftOf`), checks it (`entryErrors`) and decides when the hours are repainted (`scheduleChanged`: only when the days, whole hours, start or week types change). The store's `saveEntry` applies the draft in one step and returns the undo; `removeEntry` deletes an entry (a habit leaves its activity in place). A habit with no time keeps a count a week, not weekdays: the model has no weekday field for habits.
- **Editing rules (PRD 11.2, 11.6):** inline edit on the owning screen, one item in edit mode per screen. Every edit panel closes with Done (or Cancel for add forms) and Escape, and focus returns to the control that opened it. The week grid is the original range-select grid (FR-PLAN-23): drag or tap to select hours, then apply, edit or clear them from its action bar; it is always editable for an hourly template. Apply on a new run opens Edit range on the new block at once; its undo step waits for that edit (Save extends it, Cancel keeps the block as applied). Activities are edited inline in the Activities list (`edit=1`).
- **Year:** the planner shows one ISO year, by default the current ISO year. It is set on mount, not persisted (a reload selects the current year again). Unassigned weeks use the active template in Home and Planner (`effectiveTemplate`); the Goals comparison reads the Goals week type instead (FR-GOALS-16). The Planner Year section is collapsed by default with any number of week types (the Weeks row and the painter are inside it); with one week type its body starts with the line "Every week of <year> uses <name>.". Insights is the exception: it counts only assigned weeks, so an unassigned week is zero planned hours there (owner decision, PRD 23.1).
- **Navigation order is Home, Goals, Planner, Insights.** Home is the default tab. Week types (templates in code) are managed in the Planner's week type bar. The tab is labelled Week; its route id stays `planner`.
- **URL state.** `?tab=home|goals|planner|insights&item=<id>&edit=1`, plus `add=1&category=<id>` to open the Planner's add-activity form with a category preselected (from Goals, FR-GOALS-20). An unknown or missing tab shows Home; an unknown category falls back to the first. In code, `useNav()` gives `go(tab, target)` (pushes history), `link(tab, target)` (a NuxtLink target) and `setSelection(target)`. Nothing else is in the URL: the Home period is session state (Nuxt `useState`), the year and the Insights settings are in memory. An old `?tab=visualization` falls back to Home.
- **Week types (FR-TPL, FR-YEAR-7, FR-PLAN-25):** a week type may carry `kind: 'break'` (time off, FR-TPL-8). Goals reads the working week type while the active one is time off (`goalsTemplate`); Home, Planner and Insights do not. Presets live in `app/utils/presets.ts` (pure): Standard, Deep work, Light and Vacation, with the role mapping (sleep, work, exercise) and the habit hours kept by default for the working presets. The store has `createTemplateFromPreset`, `duplicateTemplate`, `setTemplateKind` and `setWeeksTemplate`. The optional `kind` needs no version bump.
- **Storage has no migrations.** The saved state carries `version` (`PLANNER_STATE_VERSION`, currently 8; version 8 added `alsoCategoryIds`; `kind` on a week type is optional and added without a bump). A version mismatch or an invalid or corrupt state is discarded and replaced by the seeded default. Bump the version whenever the stored shape changes. Keep the seed in `app/utils/planner.ts` a good test dataset (several categories with linked habits so the charts show real bars).
- **Onboarding (FR-ONB) is additive.** `onboarding?: 'pending' | 'done'` on `PlannerState` marks the first run. `PLANNER_STATE_VERSION` stays 8: a save without the field is never onboarded (the owner's real data included). Welcome opens only for a new user: nothing valid was loaded, or a save still says `pending` (the last session ended before the tour). A failed Supabase load does not open it. Sign-out or a user switch resets to the empty state (`$reset`) and closes the flow. `replaceState` replaces the whole state, so a previous user's journal or flag cannot carry over. The store watcher (`bind.ts`) saves `onboarding`. Tour state is session only (a reload closes it).
- **Guided path order:** 1 Your ambition, 2 Goals and habits (one or two life areas, one habit each), then the build, then the tour cards 3 Plan your week, 4 Insights and 5 Daily follow-up. The two form steps show "Step 1 of 2" and "Step 2 of 2"; the tour cards show no counter. Goals has no tour card; the Plan card explains its comparison in one sentence. The path is session state: a reload mid-way reopens Welcome while the save is `pending`.
- **UI language is English.** User-entered content can be in any language.
- **Style:** one font (IBM Plex Sans), calm blue palette, minimalist, light and dark themes. Details in `spec/frontend-design.md`. Do not reintroduce serif or mono fonts or the old terracotta accent.

## Working conventions

- **Delegate implementation to the `doer` agent** to save tokens, with explicit file paths, steps and verification. The lead session plans, reviews screenshots and reports. Give the doer a clear "commit / do not commit / push" instruction every time.
- **Commit and push only when the owner asks.** Never push to `main`. Stage specific files by name, never `git add -A`. Never touch the owner's untracked files.
- **Commit messages** are conventional (`feat:`, `fix:`, `style:`, `chore:`, `docs:`), and end with a blank line and these trailers:
  ```
  Claude-Session: https://claude.ai/code/session_01F4QzgWo6pmyzMMJzrBAvTG
  Co-Authored-By: <the model that wrote the change, as the session's attribution reminder gives it>
  ```
- **Line endings:** the working copy is CRLF and the repo stores LF. Keep CRLF on edited files.
- **Verify UI work visually.** Build for production, serve `.output/server/index.mjs`, and take headless-Edge screenshots with `puppeteer-core` installed in the session scratchpad, never in the repo. Check 1280px and 400px, light and dark, no horizontal overflow, no console errors. Look at the screenshots; do not trust only automated checks.
- **Permissions:** the owner's personal setup is in `.claude/settings.local.json` (gitignored): edits are accepted automatically, build/typecheck/read-only git are allowed, and `git push`, installs and `rm` still ask.
- **Tools on this machine:** Windows 11, Git Bash and PowerShell. The GitHub CLI (`gh`) is installed and authenticated, so PRs can be opened with `gh pr create`.

## Open items and ideas

- The intro Play button covers the centre cell of scene 1 (the Ambition cell) on phones (56px). By design, centred as asked; the owner may prefer another spot.
- **Account deletion is still by email.** Reset my data empties the planner only; the Supabase sign-in user is kept, because deleting it needs a server key. The Privacy Policy says so.

- **Supabase mode runs against the owner's real project** (Google sign-in tested locally and on Vercel, 27 October 2026). The owner's `.env` is gitignored; the agent session keeps `NUXT_PUBLIC_STORAGE=local` because it cannot sign in. Sign-in is Google only. The email link was removed on 27 October 2026: Supabase's built-in sender allows about 2 emails an hour and delivers only to team addresses. Sign-in screen: `LoginGate.vue`. Custom SMTP is the later path if email sign-in returns.

- **Hydration:** the four views in `app/pages/index.vue` render inside `<ClientOnly>` because they read the saved planner, which exists only in the browser; before this (28 October 2026) a returning save mismatched the server's empty default, with a console warning and a wrong class on the "+ New week type" button. The shell, topbar and legal pages are still server rendered. Server-side data loading would be the alternative if the views ever need server HTML.
- **Analytics:** Vercel Web Analytics as a plain script in `nuxt.config.ts` (`vercelAnalytics`, added only when `process.env.VERCEL` is set; page views only, no cookie). The `@vercel/analytics` package is not used: its peer ranges (vue-router 4, an optional Svelte and Vite 8 chain) make `npm install` fail on Vercel. The Privacy Policy has a "Visit statistics" section; keep it in step if events or other tools are added. Needs Analytics enabled in the Vercel project (done by the owner).
- **Legal pages (FR-LEGAL, feat/legal-pages):** the operator details in `app/utils/legal.ts` are filled (Juan Galvis, France, Supabase Ireland eu-west-1, French law); update `lastUpdated` and the Supabase region if either changes.
