# Timely: agent context

Shared context for any Claude Code session working on this repo. Read it first, then the specs it points to. Keep it short and current: update it when a decision, convention or open item changes.

## What this is

Timely is a local-first planning app. It combines two ideas:

- **The why (goals):** a Harada grid. One 5-year ambition, 8 life areas (categories), each with a 5-year goal, a 1-year target and measurable daily habits.
- **The time (planner):** a weekly template of hour slots, applied across the 52 or 53 weeks of the year. Today shows the day; Plan holds Dreams (the goals), Week (the template) and Year (the planned hours of one year or several, and which week type each week uses); Progress shows adherence (planned against ticked on Today).

The link between them is the product: a habit points at an activity, and Year shows where the planned hours go. Goals keeps the why and the habits (each habit's plain need, "Needs 6 h a week"). The comparison of needed and planned time was removed on 2026-10-29: the owner judged it circular, since both sides come from the same habits.

The owner is a solo developer. The app is still in dev mode: no production users, no backward compatibility needed.

## Stack and commands

Nuxt 4, Vue 3, Pinia, TypeScript. No component library and no icon font (Vuetify and MDI were removed in 0.0.2). State persists in browser `localStorage` by default; persistence is pluggable (Supabase is the optional remote mode, see below). There is no Timely backend.

```bash
npm run dev                 # dev server
npm run build               # production build; must stay clean
npx nuxi typecheck          # must stay at 0 errors
npm test                    # unit tests (Vitest, tests/unit): must stay green; npm run test:watch to watch
```

If `npx nuxi typecheck` cannot resolve vue-tsc, run `npm i --no-save vue-tsc@3 @vue/language-core@3` (never commit that to `package.json` or the lockfile).

CI (`.github/workflows/ci.yml`) runs on pull requests and on pushes to `main`: `npm ci`, `npm test`, the same typecheck (with vue-tsc installed for the run) and the build. Keep all four green. Unit tests cover the pure modules in `app/utils` (`tests/unit/*.test.ts`, shared data in `tests/unit/fixtures.ts`); new pure logic gets a test there, and tests pass dates explicitly (no clock). **Size guard:** `tests/unit/fileSize.test.ts` fails when any `.vue` or `.ts` file in `app/` passes 400 lines; split the file by responsibility instead of raising the limit.

## Security headers and CSP

- **Where:** `server/plugins/security.ts` (a Nitro plugin: the static headers on every response in the `request` hook, and a per-page Content-Security-Policy with a fresh nonce in `render:response`, which also puts the nonce on every `<script>` of the page). The pure parts are in `server/utils/security.ts` (`SECURITY_HEADERS`, `buildCsp`, `supabaseSources`, `addScriptNonce`) and tested in `tests/unit/security.test.ts`.
- **Why not routeRules:** on Vercel the route rules are also written to the platform route config, so a header could be sent twice, and a repeated nosniff or X-Frame-Options can make the browser ignore it. Keep the headers in the plugin. The Vercel CDN serves `/_nuxt` files without the function, so those files do not get the headers; the HTML and API responses do.
- **Policy:** `script-src` is `self` plus the nonce, with no `unsafe-inline` (Nuxt payload, bootstrap, importmap and the prepaint script all get the nonce). `style-src` keeps `unsafe-inline` for Vue inline styles (a known limit). `connect-src` is `self` plus the origin and wss of `NUXT_PUBLIC_SUPABASE_URL`, read from the runtime config on each request, so a build without it still works.
- **Adding an origin or a third-party script:** change `buildCsp` (and its test) first, then the code that uses it. Do not add a third-party script or origin without that line. Never add `unsafe-inline` or `unsafe-eval` to `script-src`.
- **Check it:** `curl -I` the server and read the `Content-Security-Policy` line; in the browser, a violation shows as a console error that names the directive.

## Model and decisions

- **One list of categories.** Goal dimensions and planner categories are the same thing. `Category` has `id, name, color, order` plus `goal5y, target1y, targetTbd`. The first 8 categories by `order` form the 3x3 Goals grid. Categories are managed in Goals (list and detail edit mode); activities are managed in Week. In the UI the categories are called life areas; the code keeps `category`.
- **Activities are a separate level** under a category. **Habits** belong to a category, are measurable (frequency count per day/week/month plus optional `minutesPerOccurrence`) and may link to an activity. A habit can make its own activity from its form (FR-GOALS-24, `ownActivityFor` in the store): the activity has the habit's name and life area; renaming the habit does not rename it.
- **Removed 2026-10-29: planned against needed (FR-INS-P4, FR-GOALS-16, FR-GOALS-P1, FR-GOALS-P2).** The owner judged the comparison circular: both sides come from the same habits. Removed: `categoryPlanVsNeed`, `yearPlanVsNeed`, `neededMinutesOverWeeks`, `planPeriodLabel`, `categoryAlignments`, `alignmentStatus`, `comparedActivityIds`, `scheduledWeeklyMinutesForCategory`, `PlanComparison.vue`, `PlanBadge.vue`. Kept: `habitWeeklyOccurrences` (now unused in the app), `goalsTemplate`, `scheduledWeeklyMinutesForActivity`. A time budget per life area is the later idea (Open items).
- **Activities have one primary category.** `categoryId` is the primary category: it gives the colour and the listing, and the Year shares count each activity once there, so they add up to 100. Secondary categories (`alsoCategoryIds`, "Also counts toward") were removed on 2026-10-29 with the comparison: the type no longer has the field, nothing reads or writes it, and a save that still carries it loads with the value ignored.
- **One entry, one form (FR-ITEM).** The user sees one kind of item. Entries are edited in Plan > Dreams (each life area's list) and by `?item=<id>&edit=1` on Plan > Week; the Week view has no list (2026-11-04). An entry is a habit with its linked activity, or an activity that no habit links to; the stored objects keep their shape. `app/utils/entries/` (no barrel: import the file that holds the name; `draft.ts` the draft, `validate.ts` the checks, `text.ts` the lines, `counts.ts` the counts, `rows.ts` the rows, `resolve.ts` the key lookup) reads them into one draft (`entryDraftOf`), checks it (`entryErrors`) and decides when the hours are repainted (`scheduleChanged`: only when the days, whole hours, start or week types change). The store's `saveEntry` applies the draft in one step and returns the undo; `removeEntry` deletes an entry (a habit leaves its activity in place). A habit with no time keeps a count a week, not weekdays: the model has no weekday field for habits. A confirmation (Delete, Save without time) takes focus when it opens and gives it back to the form panel when it closes, so Escape closes the confirmation first, then the form.
- **Sleep (FR-SLEEP-1 to 9).** The activity whose short code is `SLP` is the Sleep activity (`app/utils/sleep.ts`: `SLEEP_CODE`, `isSleepActivity`, `sleepActivityId`). Its code is locked and no other activity may take `SLP`; it cannot be deleted; its name, colour and life area stay editable. New planners (`createOnboardingState`, the seed, every new week type, presets) paint it 10 PM to 7 AM every night; existing saves are not migrated, and a save without it gets "Set up sleep". The Week tab's "Sleep hours" button opens the editor for the active week type (every night, or weekdays and weekend). A "Show sleep" preference (`localStorage` key `timely.showSleep`, default off, shared by Today, Week and Year) hides it everywhere: Today leaves it out, the Week grid collapses the hour rows that are sleep on all seven days, and Year and Goals leave it out of the planned hours and the available time (Year counts it under Physical when shown; Adherence does not count sleep). Sleep never counts in Goals. Planned hours never count Sleep: the awake hours (FR-SLEEP-9, `app/utils/awake.ts`) are the 168 hours less Sleep, and the Week meta line, the week type chip and the guided tour all read them. No data model change: storage version stays 8, no field was added to `PlannerState`, `Activity`, `WeekTemplate` or `settings`, and the preference lives outside the planner state.
- **Editing rules (PRD 11.2, 11.6):** inline edit on the owning screen, one item in edit mode per screen. Every edit panel closes with Done (or Cancel for add forms) and Escape, and focus returns to the control that opened it. The week grid is the original range-select grid (FR-PLAN-23): drag or tap to select hours, then apply, change, edit or clear them from its action bar. A run that holds an activity shows its edge handles at once (no Edit range step, 2026-11-05); Save applies a moved edge and is enabled only after a move; Cancel reverts a moved edge, and a clean Cancel closes the box; Edit opens the entry's form, and the box and the form close each other. Apply on a new run opens the box on the new block at once; its undo step waits for the edit (Save extends it, Cancel keeps the block as applied). Activities are edited inline in the one form, from Goals or `?item=<id>&edit=1` on the Week tab.
- **Year:** the planner shows one ISO year, by default the current ISO year. It is set on mount, not persisted (a reload selects the current year again). A week with no week type of its own is blank (`weekTemplate`, 2026-11-05: no schedule, no planned hours, nothing on Today, its awake hours count as Free in Year; the active week type is what the Week tab edits, not a fallback); Goals reads its hours from the Goals week type (`goalsTemplate`, FR-TPL-8). The Year tab's painter section is open by default (in memory only) with any number of week types; with one week type its body starts with the line "Every week of <year> uses <name>.". The Week tab has no Year section; the Week grid and "Activities and habits" are disclosures open by default, in memory only. Year and Insights count a blank week for no week type (FR-INS-P3, PRD 23.1, superseded 2026-10-28 and 2026-11-05).
- **Navigation order is Today, Plan, Progress** (FR-NAV-1, option A of `spec/ux-information-architecture.md`, chosen 2026-11-04). Today is the default. Plan has three views in this order: Dreams (the goals, the old Goals), Week (the template and its grid, the old Week) and Year. The sub-nav keeps the last Plan view of the session; a reload starts at Week. Week types (templates in code) are managed in Plan > Week's week type bar.
- **URL state (FR-NAV-2 to 5).** `?tab=today|plan|progress&view=dreams|week|year&item=<id>&edit=1`. On Plan, `view` is the Plan view, and `plan` without a valid view uses the last one. On the Year view `item` is a week type id (it is chosen in Paint with and the Apply to several weeks options open; the Week view's link after a new week type sends it). Old links still work and are rewritten once: `home` to today, `goals` to plan/dreams (its `category` is read as the item), `planner` to plan/week, `year` to plan/year, `insights` to progress; `visualization`, an unknown value or an empty tab shows Today. A URL with no `tab` is left alone (an auth code from a sign-in redirect stays). Callers name places (`today`, `plan`, `dreams`, `week`, `year`, `progress`): `go(place, target)` pushes a history entry, `link(place, target)` is a NuxtLink target and `setSelection(target)` changes the item or edit mode and keeps the place. Nothing else is in the URL: the Today day is session state (Nuxt `useState`), the Year and Progress range settings are in memory. The skip link and the focus: `#main` is the page's `<main>`.
- **Week types (FR-TPL, FR-YEAR-7, FR-PLAN-25):** a week type may carry `kind: 'break'` (time off, FR-TPL-8). `goalsTemplate` (the working week type while the active one is time off) is read by Goals' entry lines and hours (`utils/entries/rows.ts`, `scheduledWeeklyMinutesForActivity`) and by presets (keep habit hours). Presets live in `app/utils/presets.ts` (pure): Standard, Deep work, Light and Vacation, with the role mapping (sleep, work, exercise) and the habit hours kept by default for the working presets. The store has `createTemplateFromPreset`, `duplicateTemplate`, `setTemplateKind` and `setWeeksTemplate`. The optional `kind` needs no version bump.
- **Done ticks (FR-HOME-14 to 18).** `done?: Record<string, string[]>` on `PlannerState`: date key to done keys (`a:<activityId>@<startHour>` for a block, `h:<habitId>` for a habit tick). Optional, like `journal` and `onboarding`; storage version stays 8; a malformed `done` is dropped by `replaceState` (`sanitiseDone`), never rejects a save. `toggleDone` refuses future dates and malformed keys. Insights reads `done` for adherence (`utils/adherence.ts`, FR-INS-P6).
- **Storage has no migrations.** The saved state carries `version` (`PLANNER_STATE_VERSION`, currently 8; version 8 added `alsoCategoryIds`, removed 2026-10-29 with no bump; `kind` on a week type is optional and added without a bump). A version mismatch or an invalid or corrupt state is discarded and replaced by the seeded default. Bump the version whenever the stored shape changes. Keep the seed in `app/utils/planner.ts` a good test dataset (several categories with linked habits so the charts show real bars).
- **Onboarding (FR-ONB) is additive.** `onboarding?: 'pending' | 'done'` on `PlannerState` marks the first run. `PLANNER_STATE_VERSION` stays 8: a save without the field is never onboarded (the owner's real data included). The first run opens for nothing valid loaded, or a save that still says `pending` (a reload mid-way reopens Welcome). Sign-out or a user switch resets to the empty state (`$reset`) and closes it. `replaceState` replaces the whole state, so a previous user's journal or flag cannot carry over. Replay first run (Account menu, both modes) asks first when the account holds a plan (`hasUserData`); Accept is the only point that replaces it. Session state only: a reload closes the first run unless the save is pending.
- **First-run order (2026-11-05, replaces the guided path and the tour):** Welcome, then 1 your ambition, 2 one to three life areas, 3 the follow-up of the first area (Not sure picks the default), 4 a normal week, 5 hours (1 to 20), then the draft (editable ambition, targets and habit names; Accept plan), then Today with the toast. No tour cards, no intro video, no Start empty, no sample data (dev only).
- **UI language is English.** User-entered content can be in any language.
- **Style:** one font (IBM Plex Sans), calm blue palette on warm paper and cards, minimalist, light and dark themes. Details in `spec/design-system.md` (tokens, colour, motion) and `spec/frontend-design.md` (layout, screens). Do not reintroduce serif or mono fonts or the old terracotta accent.

## Working conventions

- **Delegate implementation to the `doer` agent** to save tokens, with explicit file paths, steps and verification. The lead session plans, reviews screenshots and reports. Give the doer a clear "commit / do not commit / push" instruction every time.
- **Commit and push only when the owner asks.** Never push to `main`. Stage specific files by name, never `git add -A`. Never touch the owner's untracked files.
- **Commit messages** are conventional (`feat:`, `fix:`, `style:`, `chore:`, `docs:`), and end with a blank line and these trailers:
  ```
  Claude-Session: https://claude.ai/code/session_01F4QzgWo6pmyzMMJzrBAvTG
  Co-Authored-By: <the model that wrote the change, as the session's attribution reminder gives it>
  ```
- **Line endings:** the working copy is CRLF and the repo stores LF. Keep CRLF on edited files.
- **Verify UI work visually.** Build for production, serve `.output/server/index.mjs`, and take headless-Edge screenshots with `puppeteer-core` installed in the session scratchpad, never in the repo. Check 1280px and 400px, light and dark, no horizontal overflow, no console errors. Look at the screenshots; do not trust only automated checks.
- **Permissions:** the owner's personal setup is in `.claude/settings.local.json` (gitignored): edits are accepted automatically, build/typecheck/read-only git are allowed, and `git push`, installs and `rm` still ask.
- **Tools on this machine:** Windows 11, Git Bash and PowerShell. The GitHub CLI (`gh`) is installed and authenticated, so PRs can be opened with `gh pr create`.

- **Design system rules** (the standing paragraph for every doer brief; spec/design-system.md, section 8.4, enforced by `npm test`): use only `var(--...)` tokens for colour, font size, spacing, radius, shadow, duration and z-index; no raw hex, px font sizes or z-index above 9 outside `app/assets/css/tokens.css`. New `.vue` files have no `<style>` block: put CSS in `app/assets/css/features/<area>.css` (selectors prefixed `<area>-`) and import it in `main.css` under `layer(features)`; never restyle a bare primitive selector (`.btn`, `.chip`, `.card`) there, use a contextual selector. Use existing classes and `Ui*` components before writing markup; add a new `Ui*` component only if it owns ARIA state, focus, keys or timing (CSS in `assets/css/ui/`, a style guide section, a docs row). Life area colours reach CSS only as `:style="areaVars(color)"` (`--c`, `--c-ink`). State goes in ARIA attributes; targets are at least `var(--hit)`. Animations only under `:root[data-motion="lively"]` with keyframes from `motion.css`; Calm must still show every number and state. Logic goes in `app/utils` with tests. If the design guard reports a lower legacy count, lower the baseline in `tests/unit/designSystem.test.ts` in the same commit. Add no dependency.
